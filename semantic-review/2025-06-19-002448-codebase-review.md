# Codebase review: cntui terminal UI for Apple container runtime

A TUI built on OpenTUI (Zig renderer) + React/TypeScript that wraps Apple's `container` CLI binary. The app spawns `container <subcommand> --format json` for every operation—listing, starting, stopping, deleting containers, images, volumes, and machines—and renders the results in a tabbed interface with keyboard navigation.

Watch for: polling spawns a new process every 2–3 seconds per active view with no concurrency guard (confirmed); `execJson<T>` casts parsed JSON to a TypeScript type with no runtime validation—any CLI schema change crashes mid-render (confirmed); four views share an identical fetch/select/error/keyboard pattern with no shared abstraction, diverging in safety guarantees (confirmed); `LogViewer` polls at 2s and never cancels in-flight requests on unmount (likely).

## High-level view

The exec layer uses array-based args to `Bun.spawn`, preventing shell injection. The risk shifts to parsing: every `inspectContainer`/`inspectVolume`/`inspectMachine`/`inspectImage` function calls `JSON.parse` on stdout with no schema validation, casting directly to `unknown` or a typed generic. Malformed CLI output surfaces as an unhandled runtime exception deep in a React render.

Polling in `ContainersView` fires a full process spawn every 3 seconds regardless of whether the previous call completed. `LogViewer` adds a second 2-second interval. When a user opens logs, two independent intervals run concurrently with no guard against overlapping spawns, and the `LogViewer` cleanup has a timing gap where `clearInterval` races against an already-dispatched `fetchLogs` that sets state on an unmounted component.

The four tabbed views each independently implement the same state machine: items/selected/error state, async refresh, mount effect, keyboard dispatch, and confirm-delete flow. The patterns are diverging—containers has error dismissal and sub-views; machines does destructive actions inline without confirmation.

Test coverage is integration-only: each test calls the real `container` CLI and asserts return types. No unit tests for components, no mocks of `exec`, no tests for `LogViewer` or `InspectView`. CI depends on the binary being installed.

<summary>Issues (8)</summary>

1. **Overlapping poll spawns** — `ContainersView` and `LogViewer` fire intervals without checking if a prior fetch completed. Guard with an `isFetching` ref or discard responses from superseded fetches.
2. **State-set-after-unmount in LogViewer** — `clearInterval` doesn't cancel an in-flight `fetchLogs`. If the component unmounts between spawn and response, `setLines`/`setError` fire on a dead component. Add a mounted ref or cancellation token.
3. **No JSON shape validation on CLI output** — `execJson<T>` casts `JSON.parse` output to `T` without runtime validation. A CLI schema change crashes the app mid-render. Add a lightweight assertion or schema library at the boundary.
4. **Machines view has no confirmation for destructive actions** — `MachinesView` calls `deleteMachine` and `stopMachine` directly in the keyboard handler without a `Confirm` prompt, unlike containers and volumes.
5. **Error handling inconsistency across views** — Containers shows dismissable errors; volumes/images/machines show a full-screen error with no recovery path. Unify the pattern.
6. **`dim` text attribute allocated but unused in containers view** — `const dim = createTextAttributes({ dim: true })` is declared but never referenced in `containers.tsx`.
7. **Hardcoded viewport size of 20 lines in LogViewer/InspectView** — Scroll area is fixed at 20 lines regardless of terminal height. Larger terminals waste space; smaller terminals may overflow.
8. **Tests require live `container` CLI** — No mocking of `exec`; tests are integration-only and will fail in CI without the binary and a running container service.

## Process-per-poll: spawn overhead and concurrency

`ContainersView` sets an interval at `refreshInterval * 1000` (default 3s) that calls `listContainers()`, which spawns `container list --all --format json`, reads both stdout and stderr to completion, waits for exit, then parses JSON. If the CLI takes longer than 3 seconds (e.g., the daemon is under load or recovering from sleep), the next interval fires while the previous spawn is still in flight. Two or more concurrent `Bun.spawn` calls accumulate, and their resolved `setContainers` calls arrive out of order, causing the list to flicker between states.

`LogViewer` compounds this: it polls every 2 seconds with `container logs <id> -n 200`. When a user presses `l` on a container, both the parent containers-list interval and the log-viewer interval run simultaneously—but notably the containers-list interval continues running behind the sub-view, wasting spawns on data that isn't being rendered.

```
ContainersView interval ─── spawn ─── parse ─── setState
                              │
                              ├── (3s) spawn ─── parse ─── setState (stale?)
                              │
LogViewer interval ─────── spawn ─── parse ─── setState
                              │
                              ├── (2s) spawn ─── parse ─── setState
```

Fix with a `useRef<boolean>(false)` flag checked before each fetch, or an approach that discards responses from superseded fetches. The parent interval should also pause when a sub-view is active.

## Unmount race in LogViewer

The cleanup function in `LogViewer`'s `useEffect` calls `clearInterval(polling.current)`. This stops future ticks, but a tick that already fired—where `fetchLogs` is awaiting `getContainerLogs`—will resolve and call `setLines` or `setError` after the component has unmounted. Depending on OpenTUI's reconciler behavior, this may produce a warning, a no-op, or subtle state corruption if the component is remounted with different props before the stale callback resolves.

## CLI output parsing without validation

```typescript
export async function execJson<T>(args: string[]): Promise<T> {
    const output = await exec([...args, "--format", "json"]);
    return JSON.parse(output) as T;
}
```

The `as T` is a compile-time assertion with no runtime effect. If Apple's container CLI changes its JSON schema (adds a wrapper object, renames fields, changes types), the cast silently succeeds and the app crashes when React tries to access `container.status.state` on an object that doesn't have that shape. If the CLI returns non-JSON (an error message printed to stdout instead of stderr), `JSON.parse` throws, which propagates as a generic error message with no indication of what the CLI actually returned.

A minimal mitigation: assert that the parsed value is an array where expected, or use a schema library (Zod/Valibot) at the `execJson` boundary.

## Machines view skips confirmation on destructive actions

`ContainersView` and `VolumesView` route destructive operations through a `Confirm` dialog—the user must press `y` to proceed. `MachinesView` executes `stopMachine` and `deleteMachine` directly inside the `useKeyboard` async handler:

```typescript
if (key.name === "d") {
    await deleteMachine(m.id);
    await refresh();
}
```

A single accidental `d` keypress permanently deletes a machine with no undo. This is the only view where destructive actions bypass confirmation.

## Error handling divergence

Containers view: errors are shown inline and dismissable with Escape. The polling interval continues, so the next successful fetch restores the list.

Images/Volumes/Machines views: an error replaces the entire view with a single error text node. The keyboard handler still listens for `r` to refresh, but in volumes and images the error state renders _instead of_ the list view, so the user sees no affordance to recover. A single transient CLI failure locks the user out of the tab until they switch away and back (which re-mounts and re-fetches).

## Hardcoded 20-line viewport

Both `LogViewer` and `InspectView` slice their content arrays to `lines.slice(offset, offset + 20)`. A 60-row terminal shows logs in a 20-line box with 40 rows of empty space; a 20-row terminal may have the log box overflow the available area. The terminal height is knowable at runtime via `process.stdout.rows` or a layout hook if OpenTUI exposes one.

## View abstraction and duplication

The four resource views share this pattern:

- `useState<T[]>([])` for items, `number` for selected index, `string | null` for error
- An async `refresh` function that calls a list function and sets state
- A `useEffect` that calls refresh on mount (containers also sets an interval)
- A `useKeyboard` handler with up/down/r/d key handling
- Table rendering with `col()`, selected-row highlighting, and empty-state text

The implementations are diverging in ways that create behavioral inconsistencies: containers has sub-views, error dismissal, and color-coded state; machines does async work directly in the keyboard handler with no error recovery; images uses a composite key `${img.id}-${i}` to work around duplicate IDs from the CLI. A shared `useResourceList` hook could consolidate the common state/fetch/keyboard logic while each view customizes rendering and actions.

## Test coverage gaps

No mocking layer for `exec` exists, so:

- Tests cannot run in CI without the `container` binary and a running service
- There are no tests for `LogViewer`, `InspectView`, or any component behavior
- There are no tests for keyboard interaction, error states, or the confirm flow
- `parseTOML` in config.ts has no direct parsing tests (only a "defaults when no file" test)
- Error paths in `exec` (non-zero exit, binary not found, malformed JSON) are untested
